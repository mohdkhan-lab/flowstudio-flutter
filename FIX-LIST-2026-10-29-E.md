# FIX LIST E — 2026-10-29 — credit reading reliability + pre-flight gate (for v2.44.0)

Source: owner's live in-app test 2026-10-29 evening (NSR Ep12, 5 prompts,
v2.43.0) + his words: "is ko jab credits katam hoj ya to pahle hi pata
chal jan ahcy" — when credits are finished, it must be known BEFORE.

## What was observed (live MCP evidence, 2026-10-29)
- 20:43 run (5 prompts, 2 workers) ended in ~17s: 0/5 saved, no files,
  no per-task error entries. 20:49 the app's Queue Resume ran the same
  5 again: 0/5 again.
- Live balance readings swung wildly within minutes:
  20:44 → 50/50 · 20:50 sync → 0/0 "Exhausted" · 20:55 → 50/50 again.
  So the credit reader returns 0 when the Flow page is not ready, and
  a single 0-read is enough to mark an account Exhausted.
- The header/UI kept showing the stale total (100) while live state
  said otherwise; the owner, pressing Sync/Verify himself, saw the
  app sit busy/stuck for a long time on the check.

## Fixes (all three together in ONE version, per combined-sitting rule)
1. PRE-FLIGHT CREDIT GATE (owner's explicit demand): before any run
   starts (Generate button AND generate_in_app), do a live balance
   verification of the selected accounts; if usable credits < run
   cost (prompts x rate from the real rate table), DO NOT start the
   run — show one clear line: how many credits the run needs, how
   many are actually there. No silent 0-of-N runs ever again.
2. CREDIT-READ RELIABILITY: a 0/unread balance is a SUSPECT read, not
   a fact — wait for the credits element to be ready (same
   readiness-wait pattern as the v2.41.0 download fix), re-read once
   to confirm, and only then mark Exhausted. A single flaky 0 must
   never flip an account state or poison a run.
3. HONEST TOTALS: header total and account lines show the last LIVE
   verified values only, with a visible "checking…" state while a
   sync runs and a stale marker when the last sync is old — never a
   confident big number built from stale cache.

## Notes
- Engine code path: credit check in engine/ (cookieImport/liveBrowsers
  balance read) + workerPool account eligibility + Dart Generate gate.
- Diagnosis limit: the exact per-task failure reason of the 20:43 run
  was not recorded in Activity — if fix work reveals the tasks died
  at a stage other than credit eligibility, log that stage per-task
  (that logging gap is itself worth closing in the same version).

## ADDENDUM — same night: item 2's root cause found in code, shipped alone as v2.44.0
`readLiveCreditsFromPage` (engine/flowAutomation.js) checked the
"exhausted banner" BEFORE scraping the number, and its selector was
'.credit-banner-error, .prompt-warning-button' — the warning button
exists for unrelated prompt/tile warnings, so studio opens read
"0 credits", openFlowStudio returned EXHAUSTED (a definitive status),
and workerPool retired both accounts before any submission — exactly
the observed instant 0-of-N runs with no charge and no Activity error
(the reason went only to the app log via this.log). Chrome launch was
separately proven healthy the same night (flowstudio_open_chrome on
account (16): success). v2.44.0 changes ONLY this reader's order:
number first and trusted whenever found; banner TEXT (never the
warning button alone) may stand in for zero only when no number can
be read. Single-variable repair: items 1 (pre-flight gate) and 3
(honest totals) stay for the next version, after this fix is proven
on the owner's PC.
